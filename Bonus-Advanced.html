🕵️ B1 — Threat Intelligence for Pentesters

B1.1 Why Threat Intel Matters for VAPT

Threat intel turns a tester from "find vulnerabilities" to "find vulnerabilities relevant to your client's actual threats." It informs:

  • What adversaries are targeting (ransomware gangs, APT groups)
  • Which vulnerabilities are being exploited in the wild (CISA KEV)
  • Which attack patterns are currently active
  • What TTPs (Tactics, Techniques, Procedures) defenders should expect

B1.3 Practical Workflow: "Why am I testing this?"

Threat-Informed Pentest Methodology

  1. Identify client's industry (banking, healthcare, gov, etc.)
  2. Identify likely threat actors (FIN7 attacks banks, Lazarus targets crypto, etc.)
  3. Map to MITRE ATT&CK — what techniques would they use?
  4. Prioritize vulnerable surfaces against those TTPs
  5. Test those scenarios explicitly
  6. Report with threat-context: "FIN7 was seen targeting the financial sector using this EXACT exploit"

B1.4 Mapping CISA KEV to Client Assets

# Download CISA KEV catalog
$ curl -s https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json \
   | jq '.vulnerabilities[] | {cveID, vendorProject, product}'

# Cross-reference with client's tech stack
# If client uses Apache Struts and KEV shows CVE-2023-50164 in Struts,
# that's a critical testing priority

# Automated KEV-to-tech alignment
$ nuclei -t cves/2023/ -l client_assets.txt

# Or custom Python: filter by client technology
$ python3 kev_filter.py --vendor apache --product struts

B2.3 Writing Threat-Informed Findings

Traditional finding:

SQL injection vulnerability found in /api/login. Severity: Critical.

Threat-informed finding:

SQL injection (CWE-89) allows unauthenticated database extraction on /api/login. This finding aligns with MITRE ATT&CK T1078 (Valid Accounts). The Lazarus Group (North Korea-linked APT) has used similar SQLi attacks against banking portals in 2022 (Mandiant report 2023-Q3). The finding also enables T1003 (OS Credential Dumping) if combined with subsequent lateral movement exploits. Affected threat scenario: A Lazarus-style attacker could exfiltrate the customer database in <2 hours and use stolen records for follow-on phishing.

B3.2 Red Team Engagement Lifecycle

Red Team Operations Checklist

  1. Rules of Engagement — also specifies when to stop if real attack detected
  2. Threat Intelligence — base on real adversary's TTPs
  3. Initial Recon — hours of passive + 1 day of active
  4. Initial Access — phishing, exposed services, etc.
  5. Establish Foothold — C2 framework, persistence
  6. Privilege Escalation — internal recon
  7. Lateral Movement — pivot through network
  8. Domain Dominance — Domain Admin or equivalent
  9. Mission Objectives — data exfil, defacement, financial fraud simulation
  10. Exit & Reporting — clean up, recommendations to blue team

    2. What's the difference between ACL abuse and DCSync?
    3. How do you test Active Directory in a read-only context?

    🏛 B6 — Mega Case Study Walkthroughs (5)

    B6.1 Case Study — "RetailCo" Supply-Chain Pentest

    📍 Background — Multi-Region Retail Giant

    RetailCo processes 100M transactions/year across 12 countries. Annual revenue $8B. They hire us quarterly for VAPT, including supply-chain testing this quarter. Previous pentest found a couple of medium findings; nothing major.

    Scope

    • Public face: customer ecommerce (.com, .eu, .asia)
    • Backend APIs
    • Mobile apps (iOS + Android)
    • Internal corporate network (10.0.0.0/8)
    • SaaS apps integration (Salesforce, Workday)

    Week 1 — Recon

    # Subdomain recon
$ subfinder -d retailco.com | sort -u | wc -l
# 847 subdomains

# Live hosts
$ cat subs.txt | httpx -status-code -silent -o live.txt
# 312 live HTTP services

# Tech fingerprinting
$ whatweb -a 3 retailco.com
# WordPress 6.3, WooCommerce, nginx, jQuery 3.7, PHP 7.4

# Notable findings
$ cat live.txt | grep -E "^https://" | sort
- https://shop.retailco.com (production)
- https://staging-shop.retailco.com (DEV endpoint)
- https://api-eu.retailco.com (regional)
- https://api-internal.retailco.com (no auth!)
- https://marketing-cms.retailco.com (WordPress)

    Week 2 — Test the Staging Endpoint

    The DEV/staging endpoint staging-shop.retailco.com has DevTools console exposed, full admin panel, and connects to a copy of the production database.

    # Critical discovery — staging DB has PROD PII!
$ curl https://staging-shop.retailco.com/api/search?q=...
# Returns 12M real customer records!

# Staging app uses auth bypass — debug mode
$ curl https://staging-shop.retailco.com/?debug=true
# Access to all admin functions

    Week 3 — Mobile App Discovery

    The iOS app has hardcoded API keys:

    # Extract APK
$ python3 frida-ios-dump.py com.retailco.shop

# Decompile
$ class-dump PayApp.app/PayApp
$ strings -a PayApp.app/PayApp | grep -E "sk_|ak_|key=|token=" | head

# Findings:
# sk_live_51Hx... (Stripe API key)
# API_KEY = "RETAILCO_PROD_5f4dcc3b5aa765d61d8327deb882cf99"  # MD5 = 'password'
# S3 bucket = "retailco-customer-images-prod" (public read)

    Week 4 — Internal Network Compromise

    Compromise staged via the iOS app's API key → AWS metadata service:

    # AWS S3 buckets audited
$ aws s3 ls --profile retailco-internal
# → 47 buckets, 12 of which are world-readable

# Including finance-pii bucket (3.2GB!)

# Cross-referenced with AD
$ Get-DomainUser -SPN | measure
# → 4 service accounts with weak passwords (cracked in hours)

    Final Report — 23 Critical / 18 High

    Severity#Example
    Critical23Production PII in staging, AWS keys in mobile, public S3 with finance data
    High18SSRF in loyalty API, weak AD passwords, missing MFA on admin
    Medium34Verbose errors, missing security headers, weak ciphers
    Low11Information disclosure, clickjacking

    Board Impact

    CISO initially dismissed staging exposure as "internal-only." After demonstrating live customer names/SSNs from staging DB, the board initiated a comprehensive secrets management overhaul. Estimated annual savings from breach prevention: $25M+.

    B6.2 Case Study — HospitalChain (Healthcare Pentest)

    📍 Background — HospitalChain with 14 hospitals

    Serving 2.4M patients. Sensitive HIPAA-protected data. Must comply with HIPAA Security Rule (45 CFR § 164.308(a)(8)).

    Critical Findings Discovered (Week 4)

    1. CVSS 9.9 Patient lookup API returns SSN, DOB, full medical history to any authenticated user (IDOR)
    2. CVSS 9.6 Lab results URL accessible without auth via guessed ID
    3. CVSS 9.1 Backup tapes stored unencrypted in basement — left unlocked
    4. CVSS 8.6 Cardiology systems use 15-year-old Windows XP — no patches

    Engagement Outcome — HIPAA-Driven Fixes

    • Patient lookup IDOR fixed within 14 days (Priority 1 - emergency change)
    • Lab results require authentication + 2-factor for sensitive tests
    • Tape backups encrypted, basement locked with keycard access
    • Cardiology segmentation to its own network; Windows XP upgraded to Win 10
    • Patient statement: "We are committed to protecting your information"

    Why This Matters

    A breach would have cost HospitalChain $50K–$1.5M per HIPAA violation, plus state AG fines, civil suits, reputational ruin. The pentest cost $35K.

    B6.3 Case Study — GovTech (Public Sector VAPT)

    📍 Government Tax Filing Platform

    Used by 30M citizens to file annual taxes. Strict SLAs. PII data. Required to follow NIST 800-53, FedRAMP controls.

    Findings That Changed Policy

    • MFA missing on admin — single admin password = full access
    • Session cookies don't expire — unlimited sessions
    • Tax forms downloadable by id — IDOR at scale = nation-state exposure

    Outcome

    Findings went directly to CISO + agency CIO. Within 90 days:

    • MFA rolled out across all admin (estimated 47K users affected)
    • Session token invalidation added
    • Tax form access rewritten with proper authorization

    B6.4 Case Study — CryptoExchange (Smart Contract)

    📍 Background — DeFi Protocol with $300M TVL

    A cryptocurrency exchange was about to launch a new staking smart contract. We did pre-launch audit:

    Findings (Found in 3 Days)

    1. CVSS 9.8 Reentrancy in withdraw() — could drain pool
    2. CVSS 9.1 Integer overflow in reward calculation
    3. CVSS 8.5 tx.origin used in ownership check — phishing risk
    4. CVSS 6.0 Missing event logs — no audit trail

    Outcome

    Launch was DELAYED by 6 weeks. All issues fixed. Two of the three reentrancy flaws would have allowed attackers (familiar with 2016's DAO bug) to steal ~$80M in staked value. The pentest fee was $40K. ROI: 2,000x.

    B6.5 Case Study — ManufacturingPlant (OT/ICS)

    📍 SCADA/ICS Assessment at Aluminum Plant

    Plant: 3 production lines, 250 PLCs, 4 SCADA servers. Last assessed 7 years ago.

    Critical OT Findings

    1. Engineering workstation w/ default password (vendor:vendor) — could reprogram PLCs
    2. PLC firmware from 2010 — multiple known CVEs (Pwn2Own winners!)
    3. Office network directly connected to OT VLAN — no segmentation
    4. Legacy Windows XP engineering station — no patches, no AV
    5. Modbus TCP traffic unencrypted — attacker on network can issue commands

    Risk Statement

    If compromised, attacker could:

    • Cause over-temperature in furnace → equipment damage (~$10M)
    • Drop alloy composition → reject entire production batch (~$50M)
    • Cause safety incident → worker injury

    Outcome

    Purdue Model segmentation implemented. Vendor relationships established for patch management. Engineering workstations upgraded. Annual OT retest scheduled.

    ⚠ B7 — Common Mistakes Catalogue

    B7.1 Mistakes Junior Pentesters Make (Avoid These)

    ❌ Avoid:
    1. Running aggressive scans without explicit permission
    2. Skipping the report — "I'll write it later"
    3. Not documenting evidence as you go
    4. Trusting automated tools blindly (e.g., "Nessus says no risk")
    5. Testing only "low-hanging fruit" CVEs
    6. Missing business logic flaws (focused only on tech vulns)
    7. Not aligning findings to client business
    8. Reporting false positives due to rushing
    9. Disrespecting client engineers during walk-through
    10. Violating the RoE (testing out of scope)

    B7.2 Mistakes Senior Pentesters Make

    • Assuming patterns from prior engagements will repeat
    • Not letting juniors struggle — over-mentoring
    • Skipping recon because "I know how the app works"
    • Focusing only on sophisticated vulns and missing simple auth flaws
    • Not validating test data (false positives in DevSecOps era)

    B7.3 Mistakes Managers/Directors Make

    • Treating all testers as interchangeable
    • Using only one engagement type as a template for all
    • Over-engineering processes that don't add value
    • Not staying technically — losing credibility with team
    • Micromanagement vs hands-off vice versa — balance is key
    • Not knowing your own technologies deep enough

    B7.4 Organizational VAPT Mistakes

    • Running VAPT only when auditors ask
    • One-off engagements without continuous scanning
    • Ignoring desktop, OT, mobile — testing only web
    • VAPT findings filed but no remediation tracking
    • Same vendor year after year (groupthink)
    • Bug bounty replacing penetration testing (different goals)
