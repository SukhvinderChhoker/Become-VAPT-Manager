🌍 Chapter 21 — Mobile Threat Landscape

21.1 Why Mobile VAPT is Different

Mobile apps run on constrained, sandboxed devices, but they are still vulnerable to:

  • Insecure data storage (device shared with multiple apps & users)
  • Weak cryptography (custom algorithms, hardcoded keys)
  • Insecure authentication (just JWT in shared prefs!)
  • Insufficient transport security (HTTPS only sometimes)
  • Reverse engineering (APK is open source for everyone)
  • Code tampering (signing not enforced)
  • Extraneous functionality (debug code, hidden APIs)

22.3 Hunting Common Android Issues

# 1) Insecure data storage
# After running app, explore:
$ adb shell run-as com.target.app cat databases/db.db

# Common locations:
/sdcard/Android/data/<pkg>/
/data/data/<pkg>/databases/
/data/data/<pkg>/shared_prefs/  # XML prefs
/data/data/<pkg>/files/

# 2) Hardcoded secrets in source
$ jadx app.apk | grep -iE "(api[_-]?key|secret|password|token)" -r

# 3) Insecure WebView
# Smali/Java:
WebView.loadUrl(...)
setJavaScriptEnabled(true)
addJavascriptInterface(@JavascriptInterface, "bridge")

# 4) Exported activities — call directly
$ adb shell am start -n com.target.app/.SecretActivity

# 5) Improper certificate validation
# grep for:
TrustManager (overrides ALL checks)
HostnameVerifier (always returns true)
setHostnameVerifier(SSLSocketFactory.ALLOW_ALL_HOSTNAME_VERIFIER)

22.4 Frida — Runtime Manipulation

# Setup
$ pip install frida-tools

# On Android (rooted):
$ adb push frida-server /data/local/tmp/
$ adb shell chmod 755 /data/local/tmp/frida-server
$ adb shell /data/local/tmp/frida-server &

# Hook a function — example bypass root detection
$ cat byp.js
Java.perform(function() {
  var RootBeer = Java.use("com.scottyab.rootbeer.RootBeer");
  RootBeer.isRooted.implementation = function() { return false; };
});

$ frida -U -f com.target.app -l byp.js --no-pause

# Bypass SSL pinning — universal script
$ frida -U -f com.target.app -l frida-multiple-unpinning.js

22.7 Real-Life Scenario: Banking App Security Audit

📍 Scenario — "PayOne" Banking App on Android

Findings:

  1. CVSS 9.8 JWT token stored in plaintext SharedPreferences (`auth_token.xml`)
  2. CVSS 9.1 Hardcoded AES key in `BuildConfig.AES_KEY` (value: "0123456789abcdef")
  3. CVSS 8.5 Root detection bypassed via Frida — bypassable in 2 minutes
  4. CVSS 8.0 Backup allowed — `adb backup` extracts entire app data
  5. CVSS 7.5 WebView with `setJavaScriptEnabled(true)` and bridge interface loads untrusted HTML
  6. CVSS 6.5 Cleartext HTTP allowed for some analytics endpoints

The bank released it in 2018, fixed after a 90-day disclosure. The same app was lessons-learned for their 20+ app portfolio going forward.

📐 Chapter 25 — OWASP MASVS & MASTG

The OWASP MASVS (Mobile Application Security Verification Standard) is the gold standard for mobile pentest coverage. The MASTG (Mobile Application Security Testing Guide) is the methodology.

25.1 MASVS Categories — V1 to V8 + MSTG-RESILIENCE

IDCategorySome Requirements
V1Architecture, Design & Threat ModelingDocument threat model, secure SDLC
V2Data Storage & PrivacyNo sensitive data in plaintext, encrypt with strong keys
V3CryptographyUse platform crypto, no custom algorithms
V4Authentication & Session MgmtStrong authN, secure session, biometric needs fallback
V5Network CommunicationTLS everywhere, cert pinning for sensitive apps
V6Platform InteractionWebView restrictions, IPC safety
V7Code Quality & Build SettingsNo debug code, signed release APK, ProGuard/R8
V8ResilienceAnti-tampering, anti-debugging, jailbreak/root detection

25.2 Three Verification Levels

Level 1 (L1)

Basic — block simplest attacks. Required for ALL apps.

Level 2 (L2)

Standard — defense-in-depth. Banking/health apps.

Level 3 (L3)

High-Assurance — national-security, finance, healthcare top tiers.

🏁 Chapter 26 — Real-Life Mobile Pentest Walkthrough

📍 Master Scenario — "WhatsOn" Media App (Android + iOS)

Scope: Android (com.whats.on) + iOS (id1234567890) + backend API

Type: Grey-box, 1 user premium account

Phase 1 — Setup

  • Pixel 6 rooted (Magisk), iPhone 13 jailbroken (palera1n iOS 16.5)
  • Burp Suite as proxy on Wi-Fi
  • Frida server installed on both
  • Mock backend used by API not in scope

Phase 2 — Static Analysis

# Decompile
$ apktool d whatsapp.apk; jadx whatsapp.apk
# Found in strings:
#  "https://api.whats.on/v2/" (production)
#  "https://dev-api.whats.on/" (dev endpoint still active!)
#  "secret_key=HELLOWORLD12345678" (hardcoded AES key)

# Plist (iOS)
$ plutil -p Info.plist
# NSAllowsArbitraryLoads = true → HTTP allowed globally!

Phase 3 — Dynamic with Frida

# Bypass cert pinning
$ frida -U -f com.whats.on -l universal-pinning-bypass.js

# Now traffic flows
# 1) Premium user requests /api/v2/premium-content
# 2) Response → JWT (RS256)
# 3) Reset JWT iat to future date → session never expires!

# Hook into encryption:
$ frida -U -f com.whats.on -l hook-encrypt.js
# Hooked AES_encrypt(key, plaintext) → discovered plaintext contained user email

Phase 4 — Network MITM

# Repeated premium content request → tampered response
# /api/v2/premium-content → returns video URL
# Substituted video_id → accessed PREMIUM-CONTENT-0020 (another user's premium video)
# → IDOR / BOLA confirmed!

# Also tried:
# /api/v2/users/§user_id§/profile → IDOR → access any user profile

Findings Summary

SeverityIssue
CriticalJWT never expires + signing key in client
CriticalHardcoded AES key in Android/iOS source
HighDev API endpoint still active
HighBOLA in user profile & premium content
MediumRoot detection bypassable in 90 sec

Client retested — 100% closure after 60 days.
