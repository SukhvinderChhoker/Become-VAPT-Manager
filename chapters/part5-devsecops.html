📝 Chapter 27 — Secure Code Review (White-Box VAPT)

27.1 Why Code Review Matters

Automated tools miss 60–80% of vulnerabilities. Code review by humans remains the gold standard. As a manager, you should be able to review or evaluate manual code reviews.

27.3 Methodology — How to Review 100k+ Lines of Code

5-Phase Manual Review Process

  1. Triage — Find entry points, file structure, frameworks, exposed APIs (30 min for a 100k LoC)
  2. Data flow — Trace input → sink paths (auth → DB, file → shell, request → render)
  3. Sink analysis — Find dangerous functions (eval, exec, deserialize)
  4. Trust boundaries — Find where user input crosses trust boundaries (controllers, API handlers)
  5. Business logic — Workflows, ID generation, transaction logic

27.4 Common Sink Functions to Search

# ── Java ──
grep -rE 'Runtime\.exec|ProcessBuilder|ObjectInputStream|XMLDecoder|Class\.forName|JNDI|URLConnection|HTTPRequest|SQL' src/

# ── Node.js ──
grep -rE 'eval|child_process|require\(|deserialize\(|fs\.read|punycode' src/

# ── Python ──
grep -rE 'eval\(|exec\(|os\.system|subprocess|pickle\.loads|input\(|cursor\.execute' src/

# ── PHP ──
grep -rE 'eval\(|exec\(|system|passthru|unserialize\(|file_get_contents|include\(' src/

27.5 Real-World Example: Java Deserialization Sink

// Vulnerable Java code (UserController.java)
@RequestMapping("/api/users")
public class UserController {
  @PostMapping("/upload")
  public ResponseEntity upload(@RequestParam("data") String data) throws Exception {
    byte[] bytes = Base64.getDecoder().decode(data);
    ObjectInputStream ois = new ObjectInputStream(new ByteArrayInputStream(bytes));
    User user = (User) ois.readObject();     // ← VULNERABLE!
    return ResponseEntity.ok(userService.save(user));
  }
}

// Exploit (ysoerial tool)
$ java -jar ysoserial-all.jar CommonsBeanutils1 "touch /tmp/pwned" | base64
# Send as:
curl -X POST target/api/users/upload -F "data=<base64>"
# Remote Code Execution as the web server user ✨

27.7 Code Review Checklist

  • All inputs validated server-side
  • Parameterized queries — no string concat in SQL
  • No eval(), exec(), deserialize() on untrusted data
  • Authentication checked on every protected endpoint
  • Authorization checks per resource (not per role)
  • Sensitive data encrypted at rest
  • HTTPS-only — no HTTP allowed
  • Secrets NOT hardcoded — use vault/KMS
  • Logging doesn't include sensitive data (passwords, tokens, PII)
  • Error handling doesn't leak stack traces to user

29.1 Docker Attack Surface

DOCKER ATTACK SURFACE ══════════════════════ ┌─────────────────────────────────────┐ │ Host Kernel ─ shared with containers│ └────────────┬────────────────────────┘ ▼ ┌─────────────────┐ │ Docker daemon │ ── misconfigured API └────────┬────────┘ ▼ ┌──────────────────┐ │ Image Registry │ ◄── poisoned images (supply chain) └────────┬─────────┘ ▼ ┌──────────────────┐ │ Image Build Process│ ◄── malicious Dockerfile, secrets in layers └────────┬─────────┘ ▼ ┌──────────────────┐ │ Container Runtime │ ◄── privileged, root, capabilities, mounts └──────────────────┘

29.2 Dockerfile Review — Security Smells

# ⚠ BAD Dockerfile
FROM ubuntu:latest                       # Not pinned → untrusted base
RUN apt update && apt install -y curl    # No version pin
COPY . /app                              # Includes .git/.env with secrets
RUN curl -sSL https://x.com/install.sh | bash   # Piped curl = backdoor magnet
USER root                                # Running as root
ENV API_KEY=AKIAEXAMPLE                 # Hardcoded secret
EXPOSE 22                                # Exposing SSH inside container
CMD ./start.sh                           # No exec form → no signal handling

# ✅ GOOD Dockerfile
FROM ubuntu:22.04@sha256:abc...          # Pinned & digest-pinned
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl=7.81.0-1ubuntu1.16              # Version pinned
COPY --chown=nonroot:nonroot app /app    # Restricted ownership
USER nonroot:nonroot                     # Non-root user
HEALTHCHECK CMD curl --fail http://localhost/ || exit 1
WORKDIR /app
ENTRYPOINT ["node", "server.js"]         # Exec form
# Secrets via ENV passed at runtime only

# Identify container you're in

# → contains "docker" or "kubepods"

# What mounts?
$ mount | grep -i "vol\|bind"
# → /host filesystem might be mounted!

# What capabilities?
$ cat /proc/self/status | grep Cap
# → Mask down to specific caps

# Can I reach the daemon socket?
$ ls -la /var/run/docker.sock

29.6 Real-Life Scenario: Docker.sock Leak = Cloud Takeover

📍 Scenario: AWS CodeBuild Pipeline Exposure

A developer mounted /var/run/docker.sock into a container so the container could build images. An attacker exploited a command injection inside the container. Because the container had full daemon access, the attacker:

  1. Created a privileged container with the host root filesystem mounted
  2. Read the IAM role credentials from /proc/1/environ
  3. Used the role to delete every S3 bucket & RDS in production

Cost: $400K outage + brand damage. Fix: never mount docker.sock; use BuildKit or ephemeral build environments.

30.2 K8s Pentest Checklist

  • Anonymous auth on kube-apiserver?
  • Privileged containers running?
  • Service account token automounting enabled?
  • Docker socket mounted in pod?
  • Secrets in env vars (visible in pod spec, logs)?
  • RBAC over-permissioned (cluster-admin on default SA)?
  • Network policies absent (all pods reachable)?
  • etcd open to internet?
  • Image registries with no auth?
  • Cluster admin accessed via ServiceAccount token?

30.5 Real-Life Incident: Tesla K8s Misconfig

📍 Scenario — Tesla K8s Exposed (RedLock, 2018)

Tesla's K8s admin console had no password + admin console exposed. A cryptomining group exploited the dashboard pod to:

  1. Steal AWS creds from pod env vars
  2. Get into internal admin tools (Kibana, internal database)
  3. Run a Stratum cryptominer using Tesla's compute

Tesla later found the issue after receiving alerts from CloudTrail. Today Tesla is one of the most secure cloud-native companies and has open-sourced their hardened K8s configs.

📜 Chapter 31 — IaC (Infrastructure as Code) Security

31.1 What is IaC and Why It Breaks

IaC = Terraform, CloudFormation, Ansible, Pulumi, ARM templates. These files define infrastructure. If insecure IaC is deployed, your cloud is insecure by default.

31.2 Terraform — Security Smells

# ⚠ BAD Terraform — TG-101-Q

# Public S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "company-data"
  acl    = "public-read"     # ← Everyone can read!
}

# Security group open to world
resource "aws_security_group" "allow_ssh" {
  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]    # ← SSH from anywhere!
  }
}

# RDS publicly accessible
resource "aws_db_instance" "db" {
  publicly_accessible = true        # ← DB exposed to internet
  storage_encrypted   = false
}

# IAM policy over-permissive
resource "aws_iam_role_policy" "admin" {
  policy = jsonencode({
    Statement = [{
      Effect   = "Allow"
      Action   = "*"           # ← All actions
      Resource = "*"
    }]
  })
}

31.3 Recommended Terraform Patterns

# ✅ GOOD Terraform

# Encrypted + private S3
resource "aws_s3_bucket" "data" {
  bucket = "company-data"
  # ACL no longer default
}
resource "aws_s3_bucket_public_access_block" "pab" {
  bucket = aws_s3_bucket.data.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
resource "aws_s3_bucket_server_side_encryption_configuration" "sse" {
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

# SG scoped
resource "aws_security_group" "allow_ssh" {
  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/16"]  # only internal
  }
}

32.3 GitHub Actions Hardening

# ⚠ DANGEROUS — passing untrusted PR data to shell
- run: |
    PR_TITLE=${{ github.event.pull_request.title }}
    echo "PR Title: $PR_TITLE"          # inject → ${{ }}

# ✅ SAFE — using env var
- env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: |
    echo "PR Title: $PR_TITLE"

# ⚠ DANGEROUS — third-party action uses @main (mutable)
- uses: thirdparty/action@main   # tag ref can change

# ✅ SAFE — pinned to SHA
- uses: thirdparty/action@a1b2c3d4e5f6...

33.3 Real-Life Scenario: Dependency Confusion

📍 Scenario — "TechCorp" Internal Package Hacked

TechCorp had an internal @techcorp/auth-utils package. Pentester Alex Birsan published a public npm package with the same name & higher version number. Pip/NPM installed the public one instead — which contained a token-stealing script. With one click from a developer doing "just an npm install," an attacker achieved RCE on internal CI runners.

Fix: Configure package managers to prefer private registry; pin versions; use scoped namespaces (@techcorp/* on private registry).
